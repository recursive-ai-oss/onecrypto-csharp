# Changelog

All notable changes are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- `RecursiveAI.OneCrypto.OpenPgp`, new (not yet released): the OpenPGP packet layer. Every packet of RFC 9580 §5 plus the LibrePGP OCB packet, versions 3 to 6 of keys and signatures (LibrePGP version 5 read only), all signature subpackets with critical-bit handling, the RFC 9980 post-quantum key and PKESK formats, ASCII armor (CRC optional, checked when present), and `TransferableKey`. Reading is lossless (write-back is byte-identical) and bounded by `OpenPgpLimits`; a stream reader exposes packet bodies without buffering. See `docs/openpgp.md`.
- `onecrypto sop`, new in the `onecrypto` tool: the Stateless OpenPGP CLI subcommands that need only the packet layer (`version`, `list-profiles`, `armor`, `dearmor`, `extract-cert`, `inline-detach`); the other subcommands exit 69 until their units land. `tools/oracles/` installs the oracles (GnuPG, Sequoia, RNP, OpenPGP.js, GopenPGP) and runs the OpenPGP interoperability test suite against `sop` as a scoreboard; see `docs/sop.md`.
- OpenPGP messages in `RecursiveAI.OneCrypto.OpenPgp` and `onecrypto sop`: sign, verify, encrypt and decrypt (`sign`, `verify`, `inline-sign`, `inline-verify`, `encrypt`, `decrypt`) with `PgpMessageReader`/`PgpMessageWriter` and async twins. Signatures v3/v4/v6 over RSA, DSA, ECDSA, EdDSA and the ML-DSA composites; PKESK for RSA, ECDH, X25519, X448 and ML-KEM composites; SKESK v4/v5/v6; SEIPD v1 and v2 (EAX, OCB, GCM), LibrePGP OCB data, old SED behind an opt-in, legacy ciphers decrypt-only; ZIP and ZLIB; cleartext signatures; plaintext is released only after authentication. See `docs/openpgp.md`.
- OpenPGP certificate evaluation and message grammar follow the interoperability suite's cases: hard and soft revocations, expiring bindings and revocations, user ID revocations, primary user ID, critical subpackets, empty key flags, issuer hints, and decryption only with encryption-capable keys; one-pass headers and session keys must be closed; unknown packet versions, string-to-key types and hash algorithms are skipped; armor headers may be UTF-8; the first partial chunk is at least 512 octets; ECDH recipients with non-AES key wrap or a KDF hash under SHA2-256 are refused. A platform without ML-DSA, ML-KEM or the RSA key size gives `PgpFailure.Unsupported`. Small messages no longer allocate the 64 KiB copy buffers (a 1 KiB decrypt went from 304 KB to 42 KB per call). See `docs/openpgp.md`, `docs/sop.md`.
- LibrePGP in `RecursiveAI.OneCrypto.OpenPgp`: `PgpMessageWriter.Write` now returns a `PgpWriteResult` (`Format`, `Cipher`, `Aead`, `Reason`; `WriteAsync` returns it too) and picks the container from the recipients: SEIPD v2 when all of them read it, LibrePGP OCB Encrypted Data (with version 5 SKESK for passwords) when all of them are LibrePGP keys, SEIPD v1 for a mix; `PgpWriteOptions.ForceLibrePgp` asks for OCB Encrypted Data regardless. A version 5 key signs with version 5 signatures. Reading adds version 5 keys in full (version 5 signatures, OCB-protected secret keys), GnuPG 2.5's Kyber composite (X25519 + ML-KEM-768, X448 + ML-KEM-1024) for decryption and encryption, and GnuPG's S-expression form of its secret key. See `docs/openpgp.md`.
- SHA-224 and RIPEMD-160 (verify-only) in OpenPGP: old signatures made with them verify and keys or messages whose string-to-key uses them open; new signatures with them are refused. `CryptoPolicy` knows RIPEMD-160 (SHA-1's dates in `Standard`, rejected in `Strict`). Checked against the NIST SHA-224 and the designers' RIPEMD-160 examples and against GnuPG output (`tools/oracles/oldhash-fixtures.sh`).
- BZip2 (algorithm 3) in OpenPGP messages, read only: a decompressor written from the published format, with block and stream CRC checks and a default output ceiling (128 MiB plus 1032 times the compressed octets) that raises `PgpFailure.LimitExceeded`. `tools/oracles/librepgp-fixtures.sh` and `librepgp-interop.sh` regenerate the fixtures and run the two-way checks against GnuPG and RNP.
- `SignPadesArchive`, `SignPadesArchiveAsync` and `PadesSigner.SignArchive`/`SignArchiveAsync` (`.Pdf`): sign at B-T, then add the document security store and the archive time-stamp with revocation data collected after the signature time-stamp, in one call. `PadesTimestamp.RequireReport()`, `RequireToken()` and `TryGetReport`, `TimeStampReport.RequireToken()`/`TryGetToken`, `PdfSignature.OpenSignedDataOrThrow()`/`TryOpenSignedData` and `PadesError.NotPresent`: non-nullable accessors for straight-line code.
- `TsaClient(fetcher, authority)` and `TsaClient.GetTimestampAsync` (`.Online`): a method with the shape of the bridge's `PadesTimestampFunction`, so `Timestamp = tsa.GetTimestampAsync` needs no hand-written HTTP.
- `DigestNames` (OID ↔ `HashAlgorithmName` for SHA-1, SHA-2, SHA-3 and SHAKE256), `SignedData.HashAlgorithmFor`, `HashAlgorithmName` overloads of `SignedData.CreateDetachedFromDigest` and `PrepareDetachedFromDigest`, and `DigestMismatchException` (an `ArgumentException`) naming both algorithms when a digest does not fit.
- `PrivateKey.SigningKeyFromCertificate` and `TrySigningKeyFromStore`: `ISigningKey`-typed twins of the operating-system key lookups, so `CmsSignerSpec.Key` needs no cast.
- `DistinguishedName.FromDer`, `TryFromDer`, `Parse(string)` and `TryFromString`: names that say whether the input is DER or RFC 4514 text. `Parse(bytes)` stays and still means DER.
- `TimeStampVerifyOptions.RevocationModel` and `RevocationDataTime`: judge the authority's revocation data in the past-time model.

### Changed

- ASCII armor is now written with the CRC-24 line by default (`ArmorWriteOptions.Checksum`), because GnuPG 2.4 and 2.5 reject armor without it when the data length is a multiple of 3. Readers still treat the CRC as optional.
- Trust anchors (`ValidationOptions.StrictAnchorStructure`, new): a root whose basicConstraints is not marked critical anchors a path. An anchor is a name and a key (RFC 5937 §2), so its own extensions are no longer held to the CA-certificate rules; `ValidationOptions.StrictAnchorStructure` (default false) turns that check back on. Malformed or duplicated anchor extensions still fail.
- The PAdES verifier judges the authority of a signature time-stamp in the past-time model when a trusted document time-stamp covers the stored revocation data, so a file whose data was collected after the signature time-stamp now reaches B-LTA instead of stopping at B-T.
- `SignedData.CreateDetachedFromDigest` without a key raises an `InvalidOperationException` that points to `PrepareDetachedFromDigest`.
- `CertificateAuthority.IssueCrl` still refuses a `ThisUpdate` outside the CA certificate's validity (RFC 5280 §5.1.2.4); the message now says what to do, and docs/issuance.md gives the reason.

## [0.2.0-preview.1] - 2026-11-01

Second preview. Adds path validation to the core package (still a preview; an internal review is done, an external audit is not), the issuer side, and two new packages: `RecursiveAI.OneCrypto.Online` and `RecursiveAI.OneCrypto.Pdf`. The API is not stable yet. This library has not been independently audited. What is tested, against what, and the documented deviations: [docs/conformance.md](docs/conformance.md).

### Fixed

- `SignaturePacket.IssuerKeyId` and `IssuerFingerprint` returned an empty value instead of null when the subpacket was absent, so a signature that names its issuer only by fingerprint (what GnuPG writes for version 5 keys) never matched its one-pass header.
- Verification and validation no longer raise `X509ParseException` when a received certificate, CRL or OCSP response carries an extension that cannot be decoded. `SignedData.Verify` and key-identifier matching treat such a certificate as not matching and say so in the `signer-certificate` check; the path validator skips an unusable CRL, delta CRL or CRL entry and reports the revocation as unknown; `SignedData` chain extraction and the CRL client's delta discovery ignore malformed data. `Certificate.TryGetExtension<T>` is the additive way to read an extension of a received certificate without throwing.
- In the browser runtime, AES (PBES2 and PKCS#12 decryption, CMS and OpenSSH ciphers), triple DES and RC2, and RSA, ECDSA and ECDH key objects now fail with `AlgorithmNotSupportedException` naming the algorithm and platform, not the runtime's `PlatformNotSupportedException`.
- `SshPublicKey.ToPublicKeyInfo` builds RSA and ECDSA keys from their numbers instead of through the platform, so it works where the platform has no RSA or ECDSA.

### Added

- `RecursiveAI.OneCrypto.Online`, new: a guarded HTTP transport (only `http`/`https`; certificate-supplied URLs cannot reach loopback, private, link-local, carrier-grade NAT, multicast or IPv4-wrapping IPv6 addresses, checked on the address actually connected to; timeouts, size and redirect limits applied to every hop), an RFC 9111 cache that also honours CRL and OCSP `thisUpdate`/`nextUpdate` at the caller's reference time, record and replay transports for test fixtures, clients for RFC 3161 time-stamps, OCSP (POST and the RFC 5019 GET form), CRLs with delta CRLs, and `caIssuers` certificates, and `ICertificateSource`/`IRevocationSource` implementations so `PathValidator.ValidateAsync` can fetch what is missing. Nothing is fetched unless a call asks; offline revocation stays unknown. See `docs/online.md`.
- `RecursiveAI.OneCrypto.Pdf`, new: the PDF bridge on OnePDF 1.17.1: PAdES signing from B-B to B-LTA with any `ISigningKey` (RSA, ECDSA, Ed25519, Ed448 and, as a preview, ML-DSA), where OnePDF writes the signature hole and core builds the CMS (signature time-stamp, document security store, document time-stamp; the time-stamp authority and revocation sources are the caller's); signing in two steps across processes (`PadesTwoPhase`, with a serialisable `PadesPendingSignature`); augmentation of signed files and archive time-stamp renewal; and verification that adds OneCrypto's CMS verifier, RFC 3161 verifier and path validator (past-time model through signature and document time-stamps, the store's contents, per-rule reports, the PAdES level) to OnePDF's own verdict without weakening it. For EdDSA and ML-DSA, which OnePDF does not check, the bridge's verdict is the one reported. See `docs/pdf.md`.
- `SignedData.CreateDetachedFromDigest`, `PrepareDetachedFromDigest`, `DigestAlgorithmFor` and `HashContent`: a detached CMS signature (content type, message digest, ESS signing-certificate-v2) from a digest the caller already computed, in one call or as a serialisable two-step state.
- The browser-wasm suite runs in a pinned headless Chromium and is compared case by case with Node and a native run ([docs/browser.md](docs/browser.md)).
- `Argon2Phc`: Argon2 PHC string formatting, strict parsing with typed errors, and password verification ([docs/kdf.md](docs/kdf.md)).
- `Pkcs12Contents.PrivateKeyBags`, exposing `FriendlyName` and `LocalKeyId` of private-key entries.
- A win-x64 section in the platform availability table ([docs/availability.md](docs/availability.md)).

### Changed

- `RecursiveAI.OneCrypto.Pdf` moves to OnePDF 1.17.1. `VerifyPades`, `VerifyPadesAsync`, `PadesVerifier.Verify(document, …)` and `VerifyAsync(document, …)` no longer take the file bytes: they read the document's original bytes through `PdfDocument.OpenRead()`, and a file that changed after opening gives `PadesException` with the new `PadesError.SourceChanged`. Empty page trees and signatures on documents certified with no changes allowed surface OnePDF's `PdfSigningException` (`NoPage`, `CertificationForbidsChanges`); `AllowBreakingCertification` is honoured. A failed `onepdf` check now names the refused change.

- PKCS#12 files are now written at 300,000 PBKDF2 iterations by default (`Pkcs12WriteOptions.DotNetCompatible`), which `X509CertificateLoader` opens with its default limits; the previous 600,000 made it throw `Pkcs12LoadLimitExceededException`. The old counts remain as `Pkcs12WriteOptions.StrongIncompatibleWithDotNet`. See [docs/pkcs.md](docs/pkcs.md).
- The nuget.org readme links to the changelog and licences at the release tag of the packed version.
- The validator's internal review (not an external audit) is closed: all eight findings and observations O1–O5 and O7 are fixed; O6, about report contents only, is open. See `docs/validation-review.md`. The validator stays a preview.
- `docs/policy.md` is retitled "CryptoPolicy: algorithm and key-size policy".
- `CryptoPolicy` asks by signature use: PKI signatures (certificates, CRLs, OCSP, requests) use `CryptoUse.VerifyPki`, under which `Standard` rejects SHA-1 from 2017-01-01 (flagged from 2011) while message signatures keep the later SP 800-131A dates. The validator asks the policy about CRL, delta CRL, OCSP response and responder-certificate signatures too, reports the decisions in `RevocationReport.PolicyDecisions` and the reasons data was not used in `RevocationReport.Notes`. Revocation: an authentic stale CRL that lists a certificate for a final reason gives `Revoked`; delegated OCSP responders without `nocheck` are checked against supplied CRLs; `removeFromCRL` lifts only holds. Nested CRL-signer validations share one work budget and the pool is indexed (`MaxSignerValidations`).

### Removed

- `CryptoPolicy.WebPki`: `Standard` now refuses SHA-1 in certificate, CRL and OCSP signatures from 2017, which is what the preset was for (see `docs/policy.md`). An intentional break of the preview API, recorded in `src/OneCrypto/CompatibilitySuppressions.xml`.

## [0.1.0-preview.1] - 2026-11-01

First preview of `RecursiveAI.OneCrypto`, the core package. The API is not stable yet. This library has not been independently audited. What is tested, against what, and the documented deviations: [docs/conformance.md](docs/conformance.md).

### Added

- ASN.1 (`RecursiveAI.OneCrypto.Asn1`): BER, CER and DER readers over spans and streams (indefinite lengths in constant memory), DER and streaming BER writers, limits on by default, typed errors with `Try` forms. PEM (RFC 7468).
- Primitives the platform lacks (`RecursiveAI.OneCrypto.Primitives`): Ed25519 (with ctx and ph) and Ed448 (with ph), X25519 and X448; OCB3, EAX and AES key wrap; Argon2d/i/id, scrypt and bcrypt-pbkdf with cost limits; Camellia; CAST5, IDEA, Blowfish and Twofish for decryption only. Secret-handling code avoids secret-dependent branches and table indices.
- Platform dispatch: the platform's own algorithms first; verify-only RSA and ECDSA, SHA-3/SHAKE and ChaCha20-Poly1305 fallbacks only where the platform has none; otherwise `AlgorithmNotSupportedException` naming the algorithm and platform. A generated availability table per platform ([docs/availability.md](docs/availability.md)).
- CMS (RFC 5652 and successors): SignedData, EnvelopedData, AuthEnvelopedData, AuthenticatedData, EncryptedData, DigestedData and CompressedData; every RecipientInfo form including KEMRecipientInfo with ML-KEM (preview); RSA PKCS#1 v1.5 and PSS, ECDSA, Ed25519, Ed448 and ML-DSA signers; countersignatures and ESS signing-certificate attributes; per-signer verification reports; decryption that fails closed; streaming sign, verify, encrypt and decrypt in constant memory with synchronous and asynchronous forms; two-phase signing (`PreparedSignedData`).
- PKCS#8 (plain and encrypted, PBES2 with PBKDF2 or scrypt), PKCS#12 read and write (PBMAC1 and the classic MAC; legacy PBEs read only), legacy PEM private keys, and OpenSSH public keys, private keys and certificates (`RecursiveAI.OneCrypto.Wire.Ssh`).
- Issuer side in core, as I/O-free handlers over the key interfaces with two-phase signing throughout: `CertificateAuthority` (profiles as data: root, intermediate, TLS server/client, S/MIME, code signing, OCSP signing, time-stamping; issuance from a CSR or a key; unpredictable serials; AKI/SKI, AIA and CRL-DP; CRLs and delta CRLs with numbers, reasons and issuing distribution point; the TLS validity schedule of the CA/Browser Forum requirements), `TimeStampRequest`/`TimeStampResponse`/`TstInfo`, `TimeStampVerifier` (structured report per RFC 3161 rule, the authority's certificate validated by `PathValidator` against caller-supplied anchors) and `TimeStampAuthority` (RFC 3161/5816 handler with serial source, accuracy, policy selection and failure info), and `OcspResponder` (RFC 6960 handler: CA or delegated responder, byName/byKey, nonce, multi-request, preproduced responses, errors as statuses). Two-way with OpenSSL 3.5.9 `ts`, `ocsp`, `verify` and `crl`. Docs: `docs/issuance.md`, `docs/tsp.md`, `docs/ocsp-responder.md`.
- `SignedDataVerifyOptions.Chain`: each signer and countersigner of a SignedData is validated by the path validator, with the message's certificates, CRLs and OCSP responses as untrusted input; `SignerReport.Chain` holds the validator's report and the `chain` check summarises it.
- `Crypto.Load`: one call that takes bytes, a stream or a path and returns what a key or certificate file holds, typed (`LoadedItems`): certificates and chains, CRLs, certification requests, OCSP responses, public keys, private keys as usable `ISigningKey`/`IDecryptionKey`/`IAgreementKey`, PKCS#7 certificate bags, PKCS#12 contents, OpenSSH keys, certificates and `authorized_keys`, from PEM or DER by a fixed decision table. A password callback is asked at most once per distinct secret. Bad input raises `CryptoLoadException` (or `Crypto.TryLoad`) with the formats considered. See `docs/load.md`.
- `CryptoPolicy` (`Standard`, `Strict`, dated SHA-1/MD5/RSA rules, explicit reference time, decisions with rule ids and references); key interfaces (`ISigningKey`, `IDecryptionKey`, `IAgreementKey`, `IRsaKey`) with in-memory, library-curve and operating-system backends (`PrivateKey`); `SignatureSpec`; serialisable two-phase signing (`PreparedSignature`) with two-phase certificates, requests and revocation lists. RSASSA-PSS certificates with any salt length or MGF1 hash now verify.
- X.509 models in the root namespace, immutable and lossless over the received octets: `Certificate` (with `X509Certificate2` conversion both ways), `CertificateSigningRequest`, `CertificateRevocationList` (complete, delta and indirect), `OcspRequest`, `OcspResponse`, `OcspBasicResponse` and read-only `AttributeCertificate`, with names (RFC 4514), general names, public keys and typed values for the RFC 5280 extensions; builders for certificates, requests, CRLs and OCSP messages that sign through `X509Signer`; structured signature results. See `docs/x509.md`.
- The RFC 5280 path builder and validator (`RecursiveAI.OneCrypto.Validation`), as a **preview**: per-rule reports for every path tried, revocation from supplied CRLs and OCSP responses (offline is never "good"), validation at any instant, an opt-in server-authentication profile and an opt-in side-by-side report from the platform's chain engine. It has had an internal review; its follow-ups are still landing, so don't rely on it for trust decisions yet.
- Platform gaps in AES-GCM, AES-CCM, named curves (for example Brainpool on macOS) and ML-KEM/ML-DSA keys now surface as `AlgorithmNotSupportedException` naming the algorithm and platform, never the platform's own `PlatformNotSupportedException`; the availability table lists AES-GCM and AES-CCM (macOS has no AES-CCM; AuthEnvelopedData defaults to AES-256-GCM and writes CCM only when asked).
- Package metadata, package validation, NativeAOT and browser-wasm smoke apps, fuzz targets for every parser, and benchmarks against the managed libraries this one replaces.
